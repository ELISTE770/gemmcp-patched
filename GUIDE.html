GemMCP 2.1.2-patched · Windows

התקנת GemMCP מאפס

GemMCP נותן ל־Gemini Web ידיים: הוא מחבר את הצ׳אט בדפדפן לשרת מקומי קטן שרץ על המחשב, וכך בקשה בעברית פשוטה הופכת לפעולה אמיתית — פתיחת תוכנה, קריאת קובץ, שאילתת SQL. העותק הזה מבוסס על 2.1.2 וכולל שבעה תיקוני באגים שאינם בגרסה הרשמית, ובלי ה־endpoint שמאפשר החלפת קוד ללא אימות.

איך זה עובד

התוסף מזריק לשיחה הנחיות שמתארות ל־Gemini אילו כלים קיימים. כשאתה מבקש משהו, Gemini לא עונה בטקסט אלא פולט פקודת JSON. התוסף תופס אותה, מציג לך אישור, ומעביר לשרת המקומי שמבצע בפועל.

אין צורך לגעת בקוד

שתי התיקיות שמצורפות כאן — GemMCP ו־GemMCP-extension — כבר מכילות את כל שבעת התיקונים. פשוט עקוב אחרי השלבים. פירוט מה תוקן ולמה נמצא בהמשך הדף, אם מעניין אותך.

מה צריך לפני שמתחילים

  • Node.js 18 ומעלה — בדוק עם node --version. אם אין, התקן מ־nodejs.org.
  • Chrome או כל דפדפן מבוסס Chromium (Edge, Brave).
  • Windows — השרת המקומי כתוב לפעולות Windows בלבד.
1

חלץ לתיקייה קבועה

הורד את ה־ZIP וחלץ אותו למקום שלא תזיז אחר כך — למשל C:\Users\<שם>\GemMCP. Chrome זוכר את הנתיב, והזזת התיקייה תשבור את התוסף.

אל תחלץ לתיקיית הורדות

תיקיות שמתנקות אוטומטית או מסתנכרנות ל־OneDrive גורמות לתקלות. בחר מיקום יציב.

2

התקן את תלויות השרת

פתח PowerShell בתיקיית bridge-server והרץ:

cd C:\Users\<שם>\GemMCP\bridge-server
npm install

אמורות להתקין כ־94 חבילות. עכשיו צור קובץ .env באותה תיקייה:

PORT=3000

# הרשאות ברירת מחדל בצד השרת
WIN_PERM_READ=true
WIN_PERM_WRITE=false
WIN_PERM_COMMANDS=false
WIN_PERM_APPS=true
WIN_PERM_CLIPBOARD=true

# הגבלת גישה לקבצים לעץ תיקיות אחד. השאר ריק = כל הדיסק.
WIN_ALLOWED_PATH=C:\Users\<שם>\Desktop
3

ודא שזו הגרסה המתוקנת

פתח את manifest.json שבתיקייה הראשית. שתי השורות האלה צריכות להיות שם: 

"name": "GemMCP for Gemini (patched)",
"version_name": "2.1.2-patched",

אם הן חסרות, הורדת את הגרסה הרשמית ולא את זו — ואז שבעת הבאגים שמפורטים למטה קיימים אצלך.

4

הכן תיקיית תוסף נפרדת

זה השלב שרוב האנשים נכשלים בו. אם תטען ל־Chrome את GemMCP המלאה, הוא ינסה לבלוע גם את bridge-server\node_modules — למעלה מ־1,300 קבצים שאינם חלק מהתוסף.

צור תיקייה נפרדת בשם GemMCP-extension והעתק אליה רק את אלה:

manifest.json    background.js    content.js
content.css      i18n.js          prompt.js
icons\           popup\

סך הכול 15 קבצים. manifest.json חייב לשבת ישירות בשורש התיקייה.

5

טען את התוסף ב־Chrome

  1. גש לכתובת chrome://extensions
  2. הפעל את מצב מפתח (מתג ימני־עליון)
  3. לחץ טען פריט שלא נארז
  4. בחר את התיקייה GemMCP-extension — סמן אותה בלחיצה אחת, אל תיכנס לתוכה
  5. נעץ את התוסף לסרגל הכלים דרך אייקון הפאזל
6

הפעל את שרת הגשר

לחיצה כפולה על start-bridge.bat בתיקייה הראשית. לבדיקה שהוא באוויר:

curl http://127.0.0.1:3000/api/health

התשובה אמורה להיות {"status":"ok",...}.

רוצה שיעלה לבד בכל הדלקה? הרץ את register-protocol.bat, וצור קיצור אל bridge-launcher-silent.vbs בתיקיית ה־Startup (Win+R ואז shell:startup).

שקול טוב לפני הפעלה אוטומטית

כל עוד הגשר רץ, הוא מקבל פקודות. הפעלה ידנית רק כשצריך היא הבחירה הבטוחה יותר — ראה את פרק האבטחה למטה.

7

בדוק את מתג ההרצה האוטומטית

פתח gemini.google.com ולחץ על תג GemMCP בפינה. Auto-Run Approval צריך להיות לא מסומן.

בגרסה הרשמית זה דלוק כברירת מחדל

כשהמתג מסומן, כל פקודה ש־Gemini מחליט לפלוט רצה על המחשב לפני שאתה רואה אותה. כשהוא כבוי מופיע כרטיס "אשר והרץ" עם ה־JSON המלא, ואתה מחליט. בעותק הזה ברירת המחדל הפוכה — אישור — אבל שווה לוודא בעין.

8

בדיקה ראשונה

בפאנל של GemMCP ודא ש־Windows Server מסומן כ״פעיל ומחובר״, לחץ Activate GemMCP כדי להזריק את ההנחיות לשיחה, ואז כתוב: 

פתח מחשבון

אמור לקפוץ כרטיס אישור. אשר אותו — המחשבון ייפתח, התוצאה תישלח לבד חזרה לשיחה, ו־Gemini יגיב עליה. זו הפעולה הכי לא מזיקה שיש, ולכן היא בדיקת השפיות הנכונה.

מה תוקן ולמה

שבעה תיקונים, כולם אומתו על התקנה חיה, ואף אחד מהם אינו במאגר הרשמי — גם לא ב־2.1.2. אינך צריך לעשות איתם כלום; הם כבר בקבצים. הפירוט כאן כדי שתדע מה שונה, ובעיקר כדי שתזהה מה תאבד אם תעדכן מהמאגר הרשמי.

עדכון גרסה ידרוס את הכל

update.bat מושך את הגרסה האחרונה מ־GitHub. הרצתו תחזיר את שבעת הבאגים ותחזיר את ה־endpoint שהוסר. השווה מול העותק הזה לפני שאתה מעדכן.

bridge-server/server.js ‎open_app‎ מדווח הצלחה כוזבת ונתקע

התסמין: שם תוכנה שגוי מחזיר "הופעל בהצלחה" בלי שנפתח כלום — ובמקרים אחרים הבקשה לא חוזרת לעולם ומשאירה תהליך cmd תלוי לנצח.

השורש: הקוד הסיק הצלחה מקוד היציאה של start, שמחזירה תמיד אפס. החלף את קריאת ה־exec שבתוך case 'open_app' בבדיקת קיום מראש:

const reportLaunched = () =>
  res.json({ success: true, data: { message: `היישום '${appTarget}' הופעל בהצלחה ב-Windows!` } });

const launchTarget = () => {
  exec(targetCommand, { windowsHide: false, timeout: LAUNCH_TIMEOUT_MS, killSignal: 'SIGKILL' }, (cmdErr) => {
    if (!cmdErr) return reportLaunched();

    if (cmdErr.killed) {
      return res.status(504).json({
        success: false,
        error: `פתיחת '${appTarget}' לא הסתיימה בזמן ובוטלה.`
      });
    }

    execFile('powershell.exe',
      ['-NoProfile', '-NonInteractive', '-ExecutionPolicy', 'Bypass', '-Command', `Start-Process "${targetToRun}"`],
      { timeout: LAUNCH_TIMEOUT_MS, killSignal: 'SIGKILL' },
      (psErr) => {
        if (psErr) {
          const reason = psErr.killed ? 'היעד לא הגיב בזמן' : psErr.message;
          return res.status(500).json({ success: false, error: `שגיאה בפתיחת ${appTarget}: ${reason}` });
        }
        return reportLaunched();
      });
  });
};

if (targetToRun.includes(':')) {
  // פרוטוקול: קיים רק אם ה-scheme רשום ב-Registry

אחרי כל שינוי בקוד התוסף

העתק את הקובץ המעודכן גם ל־GemMCP-extension, לחץ על אייקון הרענון בכרטיס התוסף ב־chrome://extensions, ורענן את הלשונית של Gemini. בלי זה Chrome ימשיך להריץ את הגרסה הישנה.

content.js זיהוי פקודות נחסם לנצח

התסמין: שולחים בקשה, Gemini פולט JSON תקין — וכלום לא קורה. אין כרטיס אישור, אין שגיאה.

השורש: isGeminiGenerating() החזירה true אם קיים בדף כל mat-progress-bar או mat-spinner, גם מוסתר לחלוטין. בדף של Gemini תמיד יש כאלה. מכיוון שscanForToolCalls נסוגה כל עוד היא מחזירה true, הסריקה נדחתה שוב ושוב בלי גבול.

התיקון מוסיף בדיקת נראות אמיתית, ומאפשר סריקה גם בזמן יצירה. ההגנה מפני JSON חלקי עברה לבדיקת יציבות — בלוק צריך להישאר עם טקסט זהה 700ms לפני שפועלים עליו, כך ש־JSON שעדיין מוזרם לא ייתפס באמצע.

אומת מול יצירה אמיתית: כרטיס האישור הופיע תוך 900ms בזמן ש־Gemini שידר בפועל.

content.js לולאת שליחה אינסופית

התסמין: התוסף נתקע על ממתין לסיום התשובה של Gemini ולא משתחרר, גם אחרי דקות.

ב־attemptSend, ה־return של "עדיין מייצר" יושב לפני בדיקת attempts >= maxAttempts, ולכן תקרת 90 הניסיונות לא הייתה ניתנת להשגה בזמן המתנה. נוספה תקרה נפרדת של 15 שניות, ואחריה הוא שולח בכל זאת: 

[14:18:22] ממתין לסיום התשובה של Gemini כדי לשלוח תוצאה...
[14:18:36] ג'מיני עדיין מסומן כמייצר לאחר 15 שניות – שולח בכל זאת
content.js ה־interceptor בולע את ה־Enter

התסמין: מקלידים הודעה, לוחצים Enter, וכלום לא נשלח. לפעמים ההנחיה של GemMCP נערמת בתיבה שוב ושוב.

attachUserIntentInterceptor העשיר את תוכן הקומפוזר סינכרונית בתוך הטיפול באירוע השליחה, ואז נתן לאירוע המקורי להמשיך ל־Gemini — לפני שהמודל של Angular הספיק להתעדכן. כעת האירוע המקורי נעצר, ההעשרה מתבצעת, והשליחה מופעלת מחדש אחרי 150ms. אם אין מה להעשיר, האירוע לא נוגע כלל.

content.js ברירת מחדל בטוחה ל־Auto-Run

התסמין: המתג חוזר להיות דלוק מעצמו, בלי הודעה.

isAutoExecute היה true בשני מקומות, ולכן כל אובדן של המפתח autoExecute מ־chrome.storage — למשל הסרה והוספה מחדש של התוסף — החזיר בשקט הרצה ללא אישור. שונה ל־false: המצב הבטוח הוא זה שנופלים אליו.

bridge-server/server.js ‎/api/update‎ הוסר

נוסף ב־2.1.2: endpoint שמריץ git pull או מוריד ZIP מ־GitHub ומחליף את הקוד המקומי, הכל דרך PowerShell — בלי שום אימות.

מכיוון שה־CORS מאשר גם בקשות ללא origin, כל תהליך מקומי שמגיע ל־localhost:3000 היה יכול לגרום למחשב להוריד ולהריץ קוד חדש. ה־endpoint נמחק (110 שורות), ו־triggerBridgeUpdate ב־background.js מחזירה הודעה מסבירה במקום לפנות אליו.

חובה לקרוא

מה שצריך לדעת על האבטחה

הגדרות ה־env אינן מנעול

הפונקציה resolvePermissions ב־server.js מאפשרת לגוף הבקשה לדרוס את ההגדרות בקובץ .env. בדיקה בפועל: בקשה עם permissions: {allowedPath: "C:\"} קיבלה גישה ל־C:\Windows\System32 למרות ש־WIN_ALLOWED_PATH הוגבל לשולחן העבודה. אותו דבר תקף להרצת פקודות.

המשמעות המעשית: כל תהליך מקומי שמגיע ל־localhost:3000 יכול להריץ PowerShell שרירותי כל עוד הגשר פעיל. ה־CORS מאשר גם בקשות ללא origin.

ההגנה שאמורה הייתה לסגור את זה, BRIDGE_AUTH_TOKEN, אינה שמישה — התוסף עצמו לא שולח את הכותרת x-bridge-token, ולכן הפעלתה פשוט תשבור אותו. השאר אותה מכובה.

שלוש הגנות שכן עובדות:

  • השאר את Auto-Run Approval כבוי — זו ההגנה האפקטיבית היחידה מפני פקודה שגויה.
  • הגבל את WIN_ALLOWED_PATH לעץ תיקיות ספציפי, וכבה WIN_PERM_COMMANDS.
  • הרץ את הגשר רק כשצריך, במקום הפעלה אוטומטית בכל הדלקה.
